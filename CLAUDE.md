# CLAUDE.md

## Project Overview
This repository contains a broker-agnostic financial intelligence layer designed to track investments, enforce behavioral discipline, and optimize returns for an active investor[cite: 1, 8]. The platform is tailored for an investor in their 30s based in Madrid (with planned travel across Europe and eventual relocation to Argentina), holding investments across XTB, bank accounts, and cash[cite: 1, 8].

### Core Philosophy & Product Principles
- **Radical Simplicity & UI Purity:** Prioritize progressive disclosure, zero visual clutter, and ambient data visualization[cite: 1, 8]. Avoid complicated financial jargon and dense chart cemeteries; ensure the interface is intuitive enough for anyone to understand at a glance[cite: 3, 10].
- **Broker Agnosticism (The Universal Ledger):** The platform is execution-agnostic, acting as the single source of truth by ingesting and normalizing data across any broker, bank, or institution[cite: 1, 8].
- **Behavioral Accountability:** Track investor discipline rather than raw luck by auditing user-defined rules and execution habits[cite: 1, 8].
- **Contextual Intelligence:** Correlate financial outcomes with personal life events, geographical mobility, and daily execution routines[cite: 2, 9].
- **Zero-Latency Performance:** Optimized for continuous daily peripheral monitoring with true-black contrast for OLED displays and instant rendering[cite: 2, 9].

---

## Monorepo Architecture & Technology Stack

The project is structured as a three-tier modular monolith monorepo[cite: 5, 6, 10]:
- **Frontend (`apps/web`):** React SPA built with TypeScript, Tailwind CSS, and Vite, running locally on port `5173`[cite: 6, 10]. Vite's internal development proxy routes all `/api` requests to port `3000` to eliminate CORS overhead[cite: 6, 10].
- **Backend (`apps/api`):** Express REST API in TypeScript executed with `tsx` on port `3000`[cite: 6, 10]. Handles JWT authentication, WebAuthn passkeys, financial engines, and Server-Sent Events (SSE)[cite: 3, 6, 10].
- **Data Layer:** PostgreSQL 16 running in a Docker container on port `5432`, hosted inside a Colima Linux virtual machine on macOS[cite: 6, 11]. Prisma ORM manages schemas, migrations, queries, and seeding[cite: 6].

## Environment & Development Commands

### Starting the Local Environment
Execute commands in this specific sequence[cite: 6, 11]:
1. `colima start` — Boots the background Linux VM providing the Docker daemon on macOS[cite: 6, 11].
2. `docker compose up -d` (from repository root) — Spawns the PostgreSQL 16 container on port `5432`[cite: 6, 11].
3. `npm run dev` (inside `apps/api`) — Boots the Express API server on port `3000`, establishes Prisma connections, and runs seeding if needed[cite: 6, 11].
4. `npm run dev` (inside `apps/web`) — Starts the Vite frontend dev server on port `5173` with the local proxy bridge[cite: 6, 11].
5. Access the application in browser at `http://localhost:5173`[cite: 6, 11].

### First-Time Setup (fresh checkout)
1. `cp apps/api/.env.example apps/api/.env`, then fill in the values. `.env` is git-ignored. The server will not start without `JWT_SECRET` and `USER_HASH_SALT` (there are no built-in defaults; changing the salt later orphans every account). Google sign-in also needs `VITE_GOOGLE_CLIENT_ID` in `apps/web/.env.local` (see `apps/web/.env.example`) and `GOOGLE_CLIENT_ID` in the API's `.env`.
2. Generate the field-encryption key and paste it into `PROFILE_ENCRYPTION_KEY`: `openssl rand -base64 32`. Back it up: losing it makes stored profile data unreadable. Without it the profile routes answer 503 (development only: production refuses to start).
3. `npm install` inside `apps/api` and `apps/web`, then `npx prisma generate` inside `apps/api`, then the database: a new database `npx prisma migrate deploy`; an existing development database made with `db push` is baselined once with `npx prisma migrate resolve --applied 0_init`. From then on the schema changes with `npx prisma migrate dev --name <what>`, which writes a migration under `apps/api/prisma/migrations` (commit it); production applies them with `prisma migrate deploy`.

### Shared Contracts (Zod)
- Request/response schemas are written once in `apps/api/src/contracts`. `apps/web/src/contracts` is a generated, read-only mirror: after changing a contract run `npm run contracts:sync` at the repo root. `npm run contracts:check` (also run in CI) fails if the mirror drifted.

### Exchange Rates
- Comparing living phases in different currencies converts with live rates from free, key-less public APIs: ECB reference rates (Frankfurter) and the official BCRA wholesale rate for Argentine pesos (priced through the ECB dollar). Every converted amount is labelled with its source ("Official rate", "ECB rate" or "Approximate rate"). A built-in approximate table in `infrastructure/fx/referenceFxRates.ts` is only the fallback when a live source is down. A financial/MEP peso rate is planned as a separate provider.

### Bill PDFs
- `POST /api/documents/extract` takes a PDF as the raw request body (`Content-Type: application/pdf`, max 5 MB, max 15 pages). It is read in memory by a worker thread with a time and memory limit; nothing is written to disk and nothing from the document is kept. The browser keeps its own copy for the preview. The answer is a draft (`BillingDraft`); every field the text did not state clearly is `null` and stays mandatory in the review form. A scanned PDF (no text layer) returns an empty draft: there is no OCR.
- The extraction rules are pure code in `apps/api/src/domain/documentExtraction` (locale-aware amounts, dates, vendor dictionary, categories, cadence). New senders go in `vendors.ts`.
- Saving goes through `POST /api/billing-records`. A bill that matches one already recorded (same living phase, category, period, amount and sender) answers 409 `DUPLICATE_BILLING_RECORD`; matching uses a keyed HMAC fingerprint derived from `PROFILE_ENCRYPTION_KEY`. After pulling this change run `npx prisma db push` in `apps/api` (adds `BillingRecord.fingerprint`).

### Benchmarks
- `GET /api/insights/benchmarks` compares each living phase with public statistics about its country: where the household income sits among people in the country, how much of the income housing takes against the typical household, and what the income buys at world-average prices (PPP). Every missing comparison comes back with a reason in `gaps`; nothing is guessed. Household size comes from the profile (1 adult, no children if none is saved).
- Sources, all free and key-less, behind the `StatisticsProvider` port (`infrastructure/benchmarks`): Eurostat EU-SILC for European countries (income deciles `ilc_di01`, housing share `ilc_mded01`, and the share of income that households **paying rent** spend on it, `ilc_mded02`, stored as `rentCostShare`), INDEC via datos.gob.ar for Argentina (decile means), and the World Bank for every country (PPP factor, GNI per person). Earlier providers win; the World Bank only fills what they do not publish. Add a source by writing another provider and listing it in `mountProfileFeature`.
- Statistics are public, so they are cached unencrypted in `CountryStatistics` (run `npx prisma db push` after pulling) and refreshed when older than 35 days: on demand, and by a daily job that only fetches what is stale, under a Postgres advisory lock so several servers do not repeat it. `BENCHMARK_REFRESH=off` disables the job. A provider outage never overwrites good data, and an outage is never cached as "no data".
- **Positioning card** ("Where you stand"): the primary view is three badges (`phase.standing`: COUNTRY, CONTINENT, WORLD, e.g. `Top 11% of people in Spain · Top 15% of people in the EU · Top 2% of people in the world`, a rung the data cannot place is simply absent), then up to three one-line insights (`describeBenchmarks.ts`: the rent against what people who pay rent spend, "Your rent is 38% of your income. People who pay rent in Spain typically spend 31%.", the same for the EU as a line of its own only when its typical share reads differently, otherwise merged into one line, and what the income buys against the national average), then the *other* nationalities' equivalences (`nationalityEquivalences`). Raw figures, citations (name, link, retrieved date), gaps and methodology sit in a collapsed "Data sources". **Housing is compared like for like:** only a phase with tenure `RENT`, only its rent (not utilities), only against households that pay rent (`rentCostShare`, the EU's for the continent line); an owner, someone living free, or a country with no published rent share gets no housing sentence at all (`NO_HOUSING_BASELINE` in the data sources), never a comparison with all households (those blend in owners, so a tenant would always look "above average"). It is a share, never a percentile of households (no distribution is published). **Preview before any home exists:** `GET /api/insights/benchmarks/preview?countryCode&currency[&monthlyIncomeMinor][&monthlyRentMinor]` (`BenchmarkService.preview`, public statistics only, nothing stored, household from the profile) answers the typical person's monthly income in the country (the 50th percentile, `valueAtPercentile`), where a typed income sits and how a typed rent compares; the first-time flow shows these as one quiet line per step. The card sits alone in its panel: `.benchmarks` has no rule or spacing above the heading (a test guards it). Not built: city tiers (no free source).
- **Continent and world** (`domain/standing.ts`, `infrastructure/benchmarks/worldBankPipStatistics.ts`). Continent is the **EU** for every European country (EU or not; Eurostat's EU27_2020 aggregate, `ilc_di01` in euros, `ilc_mded01` for housing, income converted to euros with the FX provider), else the person's **World Bank region** (`regionCode` read from the World Bank country API: `LCN` is labelled "Latin America & the Caribbean", `NAC` "North America", ...). World and regions come from the **World Bank Poverty and Inequality Platform** (`pip-grp`, free and key-less): the share of people below each of 19 lines (1 to 500 international dollars a day) *is* the distribution; only the latest year of real survey data counts (`estimate_type=actual`, never a nowcast) and the 2021 PPP round is pinned (`ppp_version=2021`). The person's income is placed as dollars per person per day: household income / people (adults + children) / 30.44 / the country's WDI PPP factor (`purchasing`, same 2021 ICP round) / US price rise since 2021 (`priceIndex`, taken from the year of the PPP factor). Caveats shown in Data sources: the WDI factor is GDP-based, not consumption-based like PIP's own; surveys miss the very rich, so a top place can be slightly generous. An income in a currency that is not the country's is converted through the FX provider, or the rung is left out with `CURRENCY_MISMATCH`.
- **Sync of the areas.** `EU`, `WLD` and the region codes are kept in the same `CountryStatistics` table (no schema change; rows saved before `regionCode` / `referenceDistribution` existed fail the shape check and are fetched again) and refreshed when older than ~183 days (`areaMaxAgeDays`, separate from the 35 days of countries) by the daily job under the same lock; the job derives the areas from the countries in use. The benchmark request never waits for them (a full PIP round takes ~30 s): `CountryStatisticsService.cached()` serves what is stored and starts a background fetch, so the first view after a deploy may lack the continent and world rungs (gaps `NO_CONTINENT_REFERENCE` / `NO_WORLD_REFERENCE`) until the job has run (about a minute after the server starts). An outage never overwrites good data and is never cached as "no data".
- An income in a currency other than the country's cannot be compared with national figures; the phase gets `CURRENCY_MISMATCH` instead of a wrong number. Not built yet: city-level indices (Numbeo, paid), a financial/MEP peso rate, OECD data.

### Costs, bills and income of a living phase
- **One expense wizard** (`profile/ExpenseWizard.tsx`, `ExpenseSteps.tsx`). The Living phases header has one primary "Add expense". It opens a guided flow (`WizardModal`): Start (a large PDF drop zone, or "Enter it manually"), then Sender + what it is for, Amount + how often it comes (Every month, 2, 3, 6 months, Every year, One time only), and Days. Nobody picks how it is stored: `classifyExpense` (`contracts/expenseClassification.ts`, pure, shared with the web) decides from the answers. Anything read from a PDF, a one-time expense and a bill that changes every time (electricity, gas, water, heating / cooling, taxes) is a receipt (`BillingRecord`, with its days). Rent, internet, phone, subscriptions and other that repeat with no days are a declared rate (`FixedCostItem`, renewing the cost of the same name: `costRenewal.ts`). The same with days given (a past bill) asks one last "Will this come again?": yes keeps the frequency, no stores a one-off. Days are a must for receipts and optional for rates; a one-time expense asks one day ("The day it was paid") or, if chosen, "Covers several days". A new rent bill at another price is just another bill of the same phase, averaged by `effectiveCosts`. The words "recurring" and "fixed rate" never appear in the UI. Nobody picks the home: a bill goes to the living phase whose days include the first day it covers (`lib/phaseRouting.ts`; none covering it is an error, never a guess, and the amount is read in that home's currency), a rate to the home lived in today, else the last one. Every phase card, current or past and collapsed or open, carries one "Bills & costs" button with a line "Costs €X a month" beside it; it opens that home's costs and bills (`profile/PhaseBills.tsx` → `BillsLedger.tsx`, the card owns the open state): the monthly total, what it rests on ("Worked out from 12 bills, covering <first day> – <last day>", or "No bills yet: these are the rates you declared"), how far the bills moved the costs from what was declared ("... €7 a month above what you declared"), then one row per category with its monthly cost and basis ("Average of 4 bills", "Declared rate", "You declared €45" where the bills say otherwise); a category with bills opens to its own bills (edit, remove) and the PDF drop zone sits above. All the figures come from the timeline entry (`effectiveCosts`; `declaredCostsByCategoryMinor` is the same maths with no bills), and `profile/billsSummary.ts` only groups and counts the bills. Edit and remove buttons on cost and bill rows show only on hover or `:focus-within` (always on touch screens). The screens carry no instructional subtitles: labels and empty states speak for themselves.
- **Monthly cost per category** is computed once, in `domain/effectiveCosts.ts`, from the declared costs and the bills of the same living phase; the timeline, comparisons and benchmarks all use it. Utilities (electricity, gas, water, heating / cooling) and taxes are *variable*: once a bill exists the cost is the average of all the bills, each weighing the months it covers (a tax is a year per entry, whatever the dates). Rent, internet, phone, subscriptions and other are *baselines*: the declared rate stands until bills arrive, then the cost follows the average of the latest three months of bills per sender, so a change of plan moves it gradually without splitting the phase. Each timeline entry says where a category's number comes from (`costBasisByCategory`: declared, bills or mixed, and how many bills). Taxes never show an "every year" label.
- **Date ranges and cadence.** A bill cannot cover more days than its cadence allows (35 monthly, 66 every 2 months, 100 every 3 months, 370 yearly; one-off has no limit): enforced by the shared contract and the domain, and mirrored in the form. In the form, entering both dates picks the cadence; picking a cadence while the dates are empty fills them, ending today. Rules live in `contracts/billingPeriod.ts`, the form logic in `components/profile/billForm.ts`. "Quarterly" is worded "Every 3 months" everywhere in the UI (the stored value is still `QUARTERLY`).
- **Category suggestion** (`contracts/vendorMatching.ts`, dictionary in `contracts/vendorDictionary.ts`): typing a sender, or reading a PDF, preselects category and cadence in three local layers, first hit wins: (1) senders the person already declared or logged, (2) multilingual service words ("agua", "strom", "aerotermia"), (3) a dictionary of well-known senders across Europe, the UK, North America and Latin America, using the phase's country to tell apart senders that share a name. A suggestion never overrides a pick of the person. Add a sender in the dictionary; add a word in `SERVICE_STEMS`.
- **Batch PDFs.** "Add from PDFs" takes several files (chosen or dropped). Each one goes through `/api/documents/extract` in turn and is confirmed in the same wizard, pre-filled and with the PDF beside the questions ("Bill 2 of 5", Log bill, Skip this one, Cancel to stop). A field the document did not state and nobody has filled in gets a yellow border (no text); a suggestion fills it and removes the border.
- **Income streams.** A phase has any number of `incomeStreams` (`label`, net `amountMinor` per month in the phase's currency, `startDate`, optional `endDate`); none is valid (a sabbatical has €0). Streams of one phase add up per calendar day, so jobs may overlap and a gap is simply zero (`domain/income.ts`: `monthlyIncomeOn`, `earnedIncomeMinor`, `averageMonthlyIncomeMinor`). `PATCH /api/living-phases/:id` with `incomeStreams` replaces the list; they live in the encrypted phase payload: no schema change. Phases saved with the earlier "base income + income changes" are rewritten on read as streams that pay the same on every day (`streamsFromLegacyIncome`) and saved as streams the next time they are written. Streams have no currency of their own.
- **Current rate vs phase average.** The timeline entry carries both: `monthlyIncomeMinor` / `savingsCapacityMinor` / `savingsRate` (streams paying on the as-of day; a past phase shows its last day) and `averageMonthlyIncomeMinor` / `averageSavingsCapacityMinor` / `averageSavingsRate` (what was earned over the phase, divided by the months lived). A phase card has a [Current rate | Phase average] toggle (default current: `IncomeViewToggle`, `incomeFigures` in `phaseRatios.ts`). With no income the card shows what is short each month plus a "Burn rate: -€X/mo" chip, and no percentages. The toggle appears only when the two views differ (`incomeViewsDiffer`: at least one currency unit apart); with steady pay the card says "Your pay has been steady, so today's rate is also your average." instead of a control that changes nothing, and with no income it says nothing.
- Adding a home asks for one optional "Monthly net income" (becomes a stream named "Salary" from the day the home starts); editing a home never touches its income, which is changed in the card's own Income list.
- **Ending a cost, never deleting it.** A declared cost has an optional `endDate` (its last day, in the encrypted cost payload: no schema change; older costs read as never ending). `PATCH .../fixed-costs/:id` with `endDate` ends it, with `null` brings it back. `effectiveMonthlyCosts` takes `asOf`: a cost ended before it, and the bills of the sender it was declared for, leave the monthly burn; the timeline's `totalFixedCostsMinor` still adds what ended costs cost while they ran (`endedCostsBurnedMinor`). The UI has an "End subscription" action on every cost row and an "Ends on" field in the editor; ended costs stay listed as "Ended <date>".
- **Forward projection.** A variable utility's monthly cost is the average of the bills logged, however few (one or two included), and stands for every month after until a new bill moves the average: nothing needs entering each month.
- **Every 6 months** (`SEMI_ANNUALLY`, 190-day bound) is a cadence beside monthly, every 2 and 3 months, and yearly. After pulling this change run `npx prisma db push` in `apps/api` (adds `SEMI_ANNUALLY` to the `CostCadence` and `BillingCadence` enums) and `npx prisma generate`.
- **Input hygiene** (`web/src/lib/inputFilters.ts`): amounts keep only digits and one decimal mark, years four digits, names and cities letters only (no digits); vendor and address fields accept anything, so "O2" and "4D" work. The living-phase flows show no subtitles, hide their main button while a bill is being added, and no longer ask for notes (an existing home keeps its notes).
- After pulling this change run `npx prisma db push` in `apps/api` (adds `HEATING_COOLING` to the `FixedCostCategory` enum). Bills saved earlier that cover more days than their cadence allows still display, but cannot be edited until their dates or cadence are fixed.
- `scripts/contracts.mjs` mirrors every file of `apps/api/src/contracts` (flat folder), so pure code both sides need (`billingPeriod`, `calendarDate`, `vendorMatching`, `vendorDictionary`) lives there too.

### Second Salary
- `GET /api/insights/second-salary` turns the portfolio's net worth into the monthly income it could sustain (`CONSERVATIVE_REAL_YIELD` 6% a year, over 12 months) and sets it against the monthly costs of the living phase being lived today. The maths is pure, in `apps/api/src/domain/wealthMilestones.ts`; the yield is a constant there.
- **The target is the person's own.** There is no fixed band. `PUT /api/profile/second-salary-target` (`{ monthlyMinor }`, `null` clears it, 204) saves it in the encrypted profile payload (`storedProfileSchema.secondSalaryTargetMinor`, no schema change; `PUT /api/profile` keeps it, and it never appears in `GET /api/profile`). `wealthMilestones` takes `targetMonthlyMinor` and returns `target: { monthlyMinor, progress, reached, capitalNeededMinor } | null`.
- **The card** (`SecondSalaryCard`): one plain sentence on what a second salary is, then either a "Set your target" prompt (no target yet, no bar) or one progress bar "€X / month of €Y / month" plus a line on which living costs it already covers. No ticks, no legend.
- Costs covered (internal milestones, shown only as that one line): 1 utilities, internet, phone and subscriptions; 2 rent; 3 every monthly cost ("Living Cost Autonomy"). A milestone whose cost is zero is left out. Costs come from `phaseSnapshot`, so bills move them like everywhere else.
- No milestones come back (with a `gap`: `NO_CURRENT_PHASE`, `NO_COSTS` or `CURRENCY_MISMATCH`) when the cost cannot be compared; the salary and the target are still shown. Costs are not converted to the portfolio's currency yet.
- The portfolio value arrives through the `PortfolioValueReader` port (adapter: `infrastructure/pnlPortfolioValueReader.ts`). No schema change.

### Capital Horizon (milestone targets)
- A person can save up to 3 goals (`CapitalMilestone`: id, title, `targetAmountMinor`, `capitalRequiredPercentage` 1–100, category `PROPERTY | SABBATICAL | VENTURE | CUSTOM`, `enabled`, off until configured). They live in the encrypted profile payload (`storedProfileSchema`), so there is no schema change; `PUT /api/profile` keeps them, and `PUT /api/profile/capital-milestones` replaces the whole list (204). Defaults per category are `DEFAULT_CAPITAL_REQUIRED_PERCENTAGE` (property 30, the rest 100).
- `GET /api/insights/capital-horizon` returns each goal with its pace, from `capitalMilestonePacing` in `domain/wealthMilestones.ts`: capital needed = target × percentage, gap = what the net worth lacks, months = gap ÷ the monthly surplus (income minus costs of the phase being lived) rounded up. No surplus, a deficit, or no comparable phase gives `monthsRemaining: null` and a `gap` reason; an achieved goal is always 0 months.
- The web card (`CapitalHorizonCard`) shows only enabled goals, and a quiet "+ Set a milestone target" (with Property / Sabbatical / Custom presets while none is set). Editing, deleting and creating all go through one dialog and one save of the whole list. The dialog has room (24px padding, 20px between fields) and one footer row with Cancel and Save milestone; Delete is a quiet link above it.

### Profile page (tabs)
- The page has two tabs (`ProfileTabs`, a real `tablist` with arrow keys, Home and End; the open one is remembered for the session by `lib/profileTab.ts`). **Living Costs & Career**: living phases ("Add expense" is the only solid button; "Add living phase" is outlined), phase cards, and the collapsed Demographics & Household card at the bottom. **Milestones & Positioning**: Second Salary, Capital Horizon and "Where you stand" (for the home lived in today, else the last). Before the first home and profile exist there are no tabs for a regular person, only the one button that starts the first-time flow; the administrator keeps the tab strip (the first tab then holds that same single button), so Analytics is always a tab.
- **Analytics tab (admin only).** A third tab, shown only when the sign-in answer says `isAdmin` (`lib/profileTab.ts: profileTabsFor`; a remembered Analytics tab opens as the first tab for anyone else), always a real tab, even while the administrator's own profile is empty (there is no separate section any more). It stands apart: after a divider at the end of the row, in the blue accent with a small "Admin" badge (`profile-tabs__tab--admin`, `__badge`, `__divider`; the tab keeps its plain name "Analytics" for screen readers), and its panel opens with "Admin area: only administrators see this.". It shows two figures like the home hero, Customers (registered) and Active customers (signed in during the last `ACTIVE_CUSTOMER_MONTHS` = 3 months, with the percentage and the date the window starts), from `GET /api/admin/analytics` (`hooks/useUsageAnalytics.ts`, `components/profile/UsageAnalytics.tsx`). The hook loads only while the tab is open and only for the admin; the server enforces access, the flag only decides what is shown. The demo guest is not a customer.
- A phase card always shows one line for the income paying today (`Designer · €3,200/mo`, or `No income right now · since <day>`, or `2 jobs · €X/mo`; `incomeSummary.ts`; a home already left reads in the past: `Was Designer · €2,900/mo`, `No income in this home`) and, beside it, a real "Add job" button (opens the income list with the form to add one already open) and a quiet "Income & Career" toggle for the full list (`IncomeSection`), all inside the card, without expanding it. The bars say "Left after fixed costs" (income minus the fixed costs and bills tracked here: food, transport and leisure are not counted, so it is not "saved"). Under them, at most one trend sentence (`phaseTrend.ts`, pure): the bills of the last three complete months against the three before ("Your bills rose €37 a month since August. Internet is most of it."; only with 3 or more bills in those six months and a change of at least 10% and 5 units of the currency; heating and cooling are left out as seasonal; a category is named only when it is at least half the change), else what is kept against the previous home when it moved 5 points or more. The card no longer shows "Earned" or "Fixed costs paid": they were extrapolations (one bill became years of cost) presented as fact. A cost row says where its number comes from beside its name, the same for a declared cost ("Monthly") and for bills ("Average of 3 bills"). Adding a bill or a cost shows a toast ("Electricity €62/month added. You now keep 67% (was 69%)." from the timeline before and after, `costToast.ts`); after the first home is saved a card offers Log Transaction.
- Under that card, the Demographics card is where everything the first-time flow left out is asked ("Tell us more whenever you like"); a profile with no details shows the invitation and "Add details" without opening it.

### Jobs and income lifecycle
- **Every job is its own stream** (`IncomeStream`); ending one never touches the others. A stream has an optional `kind` (`ONE_TIME` = a deposit that arrived once, such as a benefit; absent = pays every month) and, once ended, an optional `endReason` (`LAID_OFF | QUIT | CONTRACT_FINISHED | OTHER`, a label only: it changes no figure). Both live in the encrypted phase payload (no schema change); older streams read as monthly, without a reason.
- **Calculations.** A `ONE_TIME` deposit counts once in `earnedIncomeMinor` / `averageMonthlyIncomeMinor` when its day falls inside the stay and is not after `asOf`, and never in `monthlyIncomeOn` (current rate, savings capacity). After the last monthly job ends the stretch counts €0. `contracts/incomeGaps.ts` (pure, mirrored to the web) gives `incomeGaps` ("No income from X to Y"; the time before the first job is not a gap) and `jobsToCarry`. **A job does not outlive its home** (`contracts/incomeGaps.ts`: `incomeReferenceDay`, `lastPayDay`, `isPayingNow`, one rule for the API and the web): in a home the person has left, a job with no end date stopped on the home's last day, so the income list never says "Paying now" there; such a job shows its dates up to the move-out day and "Until you moved out · <day>" instead of an end reason, and has no "Bring back" (nothing was ever ended). The same reference day (the as-of day held inside the home's days) feeds the timeline and the card's summary line.
- **UI.** Each income row has "End job" (last day + reason chips) and, once ended, "Bring back"; rows are grouped Paying now / Ended / One-time deposits (`groupIncome`). The editor offers "Pays every month" or "Paid once".
- **Keeping jobs in a new home.** Adding a living phase offers the monthly jobs still paying on its first day from the home lived in just before it ("Keep these jobs?", all ticked; `carryOver.ts`, `CarryJobs`). Copies start on the first day of the new home and the originals stay; in another currency the amount must be typed again, never converted.
- **Profile page buttons.** "Add expense" and "Add living phase" share `.profile-action-button` (one footprint; `--primary` / `--outline`). Compare shows only with two or more homes; the Demographics "Edit" only while its card is open.

### Guided flows (wizards)
- **Onboarding is three questions** ("Tell us about yourself", `OnboardingWizard`, `onboardingFlow.ts`): where (country and city; the country also picks the currency, `chooseCountry`), what comes in each month after tax (optional) and what the rent is (optional, or "I don't pay rent"). They make the home lived in today (it starts today unless the person opens the quiet "Moved in earlier?" link under the city and picks the day, never a later one; tenure is `RENT`, or `OTHER` for "I don't pay rent"; income becomes a "Salary" stream, rent a declared monthly `RENT` cost) and, when the profile has no name yet, put the name the account already greets the person with into the profile (`accountName`, from the greeting in `App.tsx`): nobody is asked for it, and nothing is saved to the profile otherwise. Each answer is met with one quiet line of what public statistics already say (`onboardingKnowledge.ts` over `useBenchmarkPreview`), with its source beside it; a statistic that does not exist is not shown. Nationalities, tax residence, year of birth, household and work are asked later, from the Demographics card (defaults: 1 adult, no children, everything else empty; benchmarks use the household of the profile). A page refresh while the dialog was open brings it back on the same step (`useResumableFlow`); closing it with Cancel does not reopen it on a later visit. Adding a home (`PhaseWizard`) has three steps (where, when, money); its bills are never asked there, they are added through "Add expense" (a draft saved when the flow still had a Bills step opens on the last step and drops them).
- Adding or editing a living phase, and Log Transaction, open as a centered dialog (`components/Modal.tsx`). There are no side drawers. ### Dashboard figures, selling and holdings
- **Prices.** Open positions are valued at market price through the `PriceProvider` port (`infrastructure/market`: Yahoo Finance adapter, converted to the person's currency, cached 5 minutes; an outage is never cached). A position with no price is shown at cost and the hero says so (`pricesAvailable: false`). History before today stays at cost (no price history is kept); only today's point is at market value.
- **One definition of return** (`domain/portfolioReturn.ts`): total gain = sold profit + gain on what is still held + dividends - buying fees. Net worth = cash + open positions at market, and **net worth - money put in = total gain** always (tested). `GET /api/portfolio/stats` returns `openProfit`, `openMarketValue`, `dividends`, `pricesAvailable` and `moneyPutIn` next to `soldProfit` and `totalProfit`. Dividends arrive as deposits and are not counted as money put in.
- **The money model** (`domain/cashLedger.ts`, pure; the owner's rule). **A buy never touches cash**: its amount plus fee counts as money put in. Cash changes only through Deposit, Withdraw, **sale proceeds** (a sale always adds them to Cash) and a buy that opts in with `paidWithCash` (the "Pay with cash" box of the Buy tab, off by default), which draws on cash and brings no new money. A cash purchase without enough cash in its own currency answers 400 `INSUFFICIENT_CASH` with `currency` and `availableMinor` (`domain/errors.ts`, `contracts/transaction.ts`); cash is therefore never negative. **Cash is never stored**: it is replayed from the transactions, per currency, and the one cash figure (`cashBalance`) is those balances converted with one table (`REFERENCE_EUR_RATES`) and added up, so the hero, the Cash pills and the allocation always agree (`User.cashBalance` is no longer read or written). Money put in = deposits that are not dividends - withdrawals + buys not paid with cash. Reinvesting sale proceeds into a new buy leaves the proceeds in Cash until a Withdraw is logged, unless the buy ticks "Pay with cash".
- **Where the portfolio code lives.** `application/portfolioService.ts` (`PortfolioService`: `recordTransaction` is the command, `overview`/`history`/`cashBalance` the queries) replaced the old `lib/pnlEngine.ts`; its maths is in `domain/` (`cashLedger`, `transactionPlan`, `portfolioReturn`, `holdingLedger`, `openPosition`, `portfolioSnapshots`) and its ports are `PortfolioRepository`, `SnapshotRepository`, `InflationRates`, `PriceProvider` (`application/ports.ts`; adapters `infrastructure/prismaPortfolioRepository.ts`, `prismaSnapshotRepository.ts`, `prismaPortfolioDeps.ts`). A transaction and everything it changes (position, realized gain) are saved together or not at all. The encrypting adapter of the next phase replaces only the repository adapters.
- **Daily readings** (`PortfolioSnapshot`, `domain/portfolioSnapshots.ts`). The only source of "value over time": one reading a day (total value, holdings value, cash, money put in and the price of the world-index fund `IWDA.AS`, in one `values` column so the next phase can seal them as one payload), filed by a daily job (`application/snapshotJob.ts`, `infrastructure/snapshotSchedule.ts`: two minutes after start, then every 24 h, under the `portfolio-snapshots` advisory lock, guests skipped) **and** when the figures are read and today's is missing (a deliberate read-through; the only write a query makes). A reading valued partly at cost (a price missing) is never filed. Nothing is replayed or estimated: days nobody measured are not in the history. `GET /api/portfolio/history` answers `{ realFrom, points }` (`contracts/portfolioHistory.ts`): the stored days plus right now, each with the value, the money put in, the money moved that day and the world-index benchmark (the same money invested in the index on each day's price; `null` where no index price was known). `GET /api/portfolio/performance-periods` is gone with its panel.
- **The home hero** (`components/HeroMetrics.tsx`, decided by the pure `lib/heroSummary.ts`) puts two figures side by side at the same size, because how it is going matters as much as what it is worth: **Total value** (with "Money you put in: €X" under it, then Holdings value and Cash, which add up to it) and **Total profit** (green or red, with its percentage and "since you started", then the **inflation line** and the **story**, below). The words "Net worth", "Open positions gain", "Total return" and "cost basis" are not in the UI. A window (YTD, 1Y...) shows its own "Profit", with no story and no inflation line; its dates are written beside the picker, above the chart. No percentage is shown while no money was put in (`gain.percent` is null). Amounts show no cents from 1,000 up and always write a loss as "-€1,800" (`lib/money.ts: formatMoney`, `CENTS_HIDDEN_FROM`; `formatMinor` follows the same rule). Before the first answer the hero is a skeleton. The hero holds no period picker: it sits in the chart's header row (below), where it decides what the chart shows, and the hero's figures still follow it. The "?" beside "Money you put in" (`components/HelpTip.tsx`) opens on hover or keyboard focus (and stays on a click or tap).
- **Home insights** (all pure code in `lib/`, tests first, the locale and translator passed in; `lib/heroInsights.ts` puts the first two together for `App.tsx`). **The story** (`lib/profitStory.ts`) is one or two plain sentences in row four of the profit figure, replacing the old "Still invested / Already sold" split (that split lives on in "How this adds up"): the (at most two) holdings that earned most ("Apple and Vanguard made €94,000."), one that lost ("Nvidia is down €44,000", "lost" once sold), and "Most of your profit comes from one holding: X" when one holding is over 70% of what the holdings earned. Per-holding profit is open gain plus sold profit of the same symbol (`storyHoldings`). A loss is named only if it is over 5% of the total profit or over 1,000; nothing is said without live prices or with fewer than two holdings; it is not shown for a window or while the inflation switch is on (holding profits are not adjusted, the hero is). The world-index clause ("The same money in a world index fund would be worth €23k less today, before fees and tax.", symmetrical, "about the same" under 1%) appears only once `history.realFrom` is at least twelve months old. All limits are named constants at the top of the module. Facts only: never advice, never "mistake", never red for being behind. **The inflation line** (`lib/inflationLine.ts`): "+38.40% before inflation, +9.60% after inflation" under the percentage, only for the whole history, once the oldest holding (open or sold, `portfolioAgeDays`, from the stats, not from the readings, which start at sign-up) is a year old and money was put in; with the switch on it says only "before inflation" (the hero is already adjusted); the title says which country's rise it rests on.
- **Home load failure** (`hooks/usePortfolio.ts`, `lib/emptyAccount.ts: homeView`). `usePortfolio` answers a `status`: `loading` (no answer yet), `ready` (stats and history both answered, or the last answer of this session is remembered) or `failed` (it could not and there is nothing good to show). `homeView(status, stats)` decides the screen: `loading` shows the hero skeleton, `failed` shows `HomeLoadError` (calm message and a "Try again" button that calls `refresh`), and only a successful answer with nothing in it shows the "Add your first purchase" card, so a person with money in the app never sees it because of an outage. - **Selling.** `POST /api/transactions` with `SOLD` answers 400 (`INSUFFICIENT_HOLDINGS`, with `availableUnits`) when the instrument is not held or the units would not be covered on that date or at any later sale (`domain/holdingLedger.ts`). The Sold tab lists only owned holdings (`OwnedHoldingPicker`), locks asset class, sector and region, and offers `Available: X units` with MAX.
- **Correcting and removing a transaction** (`PATCH` and `DELETE /api/transactions/:id`, both 204, owner only: another person's id is a 404). The ledger is the source of truth, so positions and realized gains are derived and rebuilt: `domain/ledgerAmendment.ts` (pure) checks that the **whole ledger still adds up** after the change and rebuilds the instrument by replaying its purchases and sales through `planTransaction` (a ledger rebuilt after a correction ends where the same ledger recorded in order would have). Editable: date, units, amount, fee, `paidWithCash`, notes; the instrument, the kind and the currency never change (delete and log again). A change that would leave a sale without its units or a cash purchase without its cash is refused: when the changed transaction is itself the one that stops holding, with the usual `INSUFFICIENT_HOLDINGS` / `INSUFFICIENT_CASH`; when a later one depends on it, with 409 `TRANSACTION_REQUIRED_BY_LATER` and `dependent: { id, type, symbol, date }`. Only breaks the change *introduces* are blamed (older data that was already off never blocks an unrelated edit); on one instant purchases come before sales and cash in before cash out. `PortfolioRepository.amend` saves the row and the rebuilt position and gains in **one database transaction**. **Snapshots:** the stored daily readings from the first day a change reaches (or today, if older) onward describe a ledger that no longer exists, so they are deleted (`SnapshotRepository.deleteFrom`) and today's is filed again on the next read: **a correction loses the value history from that day on** (an honest gap, never a line drawn from figures that were not true). The web: every history row has Edit (the same `TransactionForm` in `editing` mode: instrument and kind shown not asked, only the changed fields are sent) and Delete (`DeleteTransactionButton`: one question naming what is removed and what is recalculated, Cancel has the focus); refusals are worded by code in `lib/serverMessages.ts`; `lib/transactionRows.ts` holds the pure parts (`correctionOf`, `deleteConsequence`, `cashHeldIn`).

### Sign-in and sessions
- **Google** (`POST /api/auth/google`) takes only `{ accessToken }`. The server asks Google about the token (`getTokenInfo`), refuses it unless it was issued to this app (`GOOGLE_CLIENT_ID` is the audience; empty means Google sign-in answers 503 and is never verified without an audience) and its email is verified. Anything else in the body is ignored. Accounts are still found by the HMAC of the verified email.
- **Google is the only way to create an account.** The login has no email field. A **passkey** (Touch ID, Face ID) is an optional extra added afterwards by someone who is signed in: `POST /api/auth/passkey/register/options` and `.../register/verify` (both need the session; the account comes from the token, never the body) save one discoverable passkey in the account's row (one per account, `PASSKEY_ALREADY_ADDED` otherwise). It then signs in with no email: `POST /api/auth/passkey/sign-in/options` answers `{ challengeId, options }` (no `allowCredentials`), `.../sign-in/verify` takes `{ challengeId, credential }` and finds the account from the credential id (`PasskeyStore`, `infrastructure/simpleWebAuthnPasskeys.ts`); the counter is checked and moved on. Challenges live 5 minutes and work once (`infrastructure/passkeyChallenges.ts`). The administrator's identity can neither add nor use a passkey (`PASSKEY_NOT_FOR_ADMIN`), and neither can a demo guest (`PASSKEY_NOT_FOR_GUEST`). A passkey sign-in carries no email: the web app puts back the name remembered from the last Google sign-in on that device (`lib/rememberedUser.ts`) and labels the passkey with the email inside the browser only. The "Add a passkey" key sits in the top bar (`components/AddPasskeyButton.tsx`) until the account has one.
- **Every refusal has a code.** Sign-in, passkey and demo answers are `{ error, code }` with the code from `contracts/auth.ts` (`SIGN_IN_ERROR_CODES`); the web app words each in the language on screen (`lib/serverMessages.ts` does not compile if a code has no words). Whatever the passkey library says when it refuses never reaches the person.
- **Human check (hCaptcha, free tier).** Guards only `POST /api/auth/google` (the way accounts are created). The demo is never checked and its button is always on; passkeys need an account already. On only when `HCAPTCHA_SECRET` and `HCAPTCHA_SITEKEY` are both set (one without the other stops the boot; neither means no widget and no check, so tests need no keys). The request carries `captchaToken` in its body (`captchaBodySchema`, `contracts/auth.ts`); `captchaGate` (`routes/captcha.ts`) runs after the rate limit and asks the `CaptchaVerifier` port (`application/ports.ts`; adapter `infrastructure/hcaptchaVerifier.ts`: form POST to `api.hcaptcha.com/siteverify` with secret, answer, `remoteip` and sitekey, 3 s timeout, Zod-parsed answer). Fail closed: a missing, forged, reused or expired answer is 400 `CAPTCHA_FAILED`; an outage, an error status, a malformed answer or a wrong secret/sitekey pair is 503 `CAPTCHA_UNAVAILABLE`. `GET /api/config` answers `captchaSiteKey` (public; null when off), so the same image works anywhere and the web needs no build-time key. **Nothing is drawn on the login screen.** The check is invisible and runs after the click: "Continue with Google" opens Google's popup first (it needs the click gesture), and only once Google has given its token does `useHumanCheck.solve()` run the check (`components/HumanCheck.tsx`, the only file that knows the vendor `@hcaptcha/react-hcaptcha`, invisible mode, dark theme, no vendor telemetry; a challenge appears only if hCaptcha wants one), then the token and the check answer go to the API together. The check is reset after every attempt, failures included (an answer works once). Closing the challenge sends nothing and says "The security check was not completed. Try again." A script that cannot load shows a calm sentence and "Try again". **Keys:** local development uses hCaptcha's public TEST credentials (sitekey `10000000-ffff-ffff-ffff-000000000001`, secret `0x0000000000000000000000000000000000000000`) in the gitignored `apps/api/.env`, because hCaptcha refuses real keys on `localhost`; real keys go only in production's `.env.production` and the hCaptcha dashboard must list every domain the app is served from. Tests use the test credentials or plain fakes. Never commit real keys.
- Every sign-in endpoint (Google, both passkey sign-in steps, adding a passkey, the demo) shares one limit of 20 attempts per 10 minutes per `req.ip` (429 `TOO_MANY_ATTEMPTS` with `Retry-After`); set Express `trust proxy` when deploying behind one.
- **The demo ("Try the demo").** Each `POST /api/auth/demo` creates an account of its own (`User.isGuest`, `guestExpiresAt`, no identity hash, no email) filled by `DemoGuestSeeder`: the demo portfolio (`domain/demoPortfolio.ts`, written by `PrismaDemoPortfolio`) and, where the server has an encryption key, a full profile (two homes, income, bills, two goals, a second-salary target: `domain/demoProfile.ts`, saved through the same services real accounts use, so it is stored sealed) and an **illustrative value history** so "Value over time" and every period chip have something to show: `domain/demoHistory.ts` (`demoSnapshotHistory`, pure, deterministic, no clock) builds one `PortfolioSnapshot` a week from the first demo transaction to two months before yesterday and one a day after that, up to yesterday (today's reading is taken live like any account's); cash and money put in are replayed exactly from the demo ledger (`DEMO_LEDGER`, the same rows the guest's transactions are written from, buys paid with cash), each holding follows a smooth price path through the price of every purchase and ends at today's market price (the demo's own `DEMO_REFERENCE_PRICES` where the market cannot be read within 2.5 s), so the last seeded day agrees with the live hero (tested). It is demo-only and labelled as such here: real accounts only have readings really taken, from sign-up. Visitors never see or change each other's data. The guest's session is a one-hour token (`guest` claim, never admin); the account is erased when the guest signs out (`POST /api/auth/demo/end`, only for guests) and by a sweep every five minutes under a Postgres advisory lock (`infrastructure/guestSweepSchedule.ts`), which also erases the one shared guest account earlier versions left behind (the migration marks it expired). `routes/guestGate.ts` makes a guest's token stop working the moment the account is gone (401 `GUEST_SESSION_ENDED`; the web app then returns to the sign-in screen and says so). At most 50 guests live at once (`DEMO_BUSY`). Guests are never customers in the analytics (`isGuest`).
- **Administrator and analytics.** The administrator is whoever signs in with Google as an email listed in `ADMIN_EMAILS` (apps/api/.env, never in the repo; compared by HMAC like every identity). Only a Google-verified sign-in gets the admin claim in its session token (`isAdmin` in the sign-in answer shows the web tab); passkeys are refused for that identity (`PASSKEY_NOT_FOR_ADMIN`), so registering one cannot claim it. `GET /api/admin/analytics` (`UsageAnalyticsService`) checks the claim and that the account is still an administrator, then answers `{ registered, active, activePercent, activeSince, asOf }`: customers are accounts except the demo guests (`User.isGuest`), active means `User.lastLoginAt` within the last 3 calendar months (`domain/usageAnalytics.ts`). `lastLoginAt` is set on every real sign-in (never for the guest); after pulling this change run `npx prisma migrate deploy` in `apps/api` (`npx prisma db push` in development); accounts that existed before it count as registered, and as active after their next sign-in.
- Known gaps: sessions are 30-day JWTs in `localStorage` with no revocation, challenges and limits are in memory (one API instance).

### Accessibility, touch and phones
- **Text and contrast.** The smallest text anywhere is 13px (`--text-xs`, also the chart canvas); `--text-muted` is `#8A8A93` (about 6:1 on the black ground). New CSS uses the token, never a smaller size.
- **Touch.** `--touch-target` is 44px. Under `pointer: coarse` every button, chip, tab, field and dialog button reaches it (rule blocks "Touch screens" at the end of `index.css` and `profile.css`); on a mouse they keep their quieter size. Links inside a running sentence ("choose PDFs", "tell us about yourself") are exempt, as the WCAG target-size rule allows.
- **Focus is a border, never an outline.** No stylesheet draws `outline` or `outline-offset` (a test guards it): a focused field, button or chip changes its own border to `--border-focus` (with a 1px inset shadow so it reads as a border and never shifts the layout). A box that holds a bare input (`.money-field`, `.holdings-search`) shows it on the box only, so no ring is ever doubled.
- **Keyboard.** `SkipLink` is the first tab stop on Home and the profile page and jumps to the page's one `<main id="main-content">`. Pages are routed by the URL hash, so it moves focus by script and never changes the address. Escape closes a list of suggestions (`TransactionForm`, `OwnedHoldingPicker`) before it closes the dialog.
- **Chart.** The canvas is `role="img"` with a one-sentence summary (`lib/chartSummary.ts`: where the line starts and ends, with the days), and the world-index legend entry has a "?" (`HelpTip`).
- **Header.** The name of the app on the left (`app-header__lead`) with, for the demo guest only, the "Demo" chip right beside it; then two groups on the right (`app-header__inflation`: the switch and the "Inflation: Spain" chip; `app-header__tools`: the language icon, Log Transaction, passkey, profile with its word beside it, sign-out). On a phone (up to 520px) there are two rows for everyone, guest or not: the inflation group first, then the tools on the right, with the Demo chip (the name is hidden there, so the chip is all the lead holds, and nothing at all for a real account) at the left of that second row, so a guest header is exactly as tall as any other (121px); the groups of `app-header__actions` flow in the header's own rows there (`display: contents`) and CSS `order` places them. The switch keeps a short word ("Inflation"), the profile keeps only its mark and its accessible name. Sign-out is one click (`SignOutButton`): nobody is asked twice.
- **Phones (under 700px).** Holdings and the transaction history become cards (`NARROW_SCREEN_QUERY`); under 520px the profile tabs share the width and wrap. Nothing scrolls sideways at 390px.
- **Log Transaction.** The Sell tab asks only what is sold; its asset class, sector and region appear as plain text once a holding is picked (`.tx-locked`). Crypto is an asset class and has no sector (`lib/assetClasses.ts`). The dialog's icon and every amount follow the person's currency (`currency` prop, `lib/currencyIcon.ts`); a currency with no sign of its own is written with its code, never with another currency's sign.

- **Using them.** Components call `const { t, locale } = useTranslation()` and write `t('header.signOut')`. Without a `LocaleProvider` (tests, isolated components) everything reads in English, so existing tests do not change. Pure code that words something (`heroSummary`, `greetingFor`, `formatMonths`, the form validators, `describe*`) takes a translator as its last argument and defaults to `translateEnglish` or, for helpers called from many places, to `currentTranslator()` (the language chosen on screen). `LocaleProvider` keeps the choice in `localStorage` (a saved choice, else any Spanish browser gets `es-AR`, else English), sets `<html lang>`, and tells the formatters through `i18n/activeLocale.ts`.

Arrow keys, Home, End, Escape and Tab work, a click elsewhere closes it, choosing closes it, and focus returns to the icon. It sits in the top bar, the profile header and the sign-in screen, and meets the 44px touch size on touch screens.

Add an entry under `data.<kind>.<value>` in both catalogs.

### Tests
- `npm test` (inside `apps/api` or `apps/web`) is hermetic: no network, no database.
- `npm run test:integration` (inside `apps/api`) needs `TEST_DATABASE_URL` pointing at a disposable database (with the migrations applied: `DATABASE_URL=$TEST_DATABASE_URL npx prisma migrate deploy`), never your real data. CI runs it against a Postgres service container and also builds the three production images.

### Production (one small always-on machine, Docker Compose)
Built for a Raspberry Pi 4/5 (arm64) with a few users; nothing in it is specific to one host. How the web port reaches the internet (tunnel, reverse proxy, domain, TLS) is a separate choice made outside this file.
- **Bring it up.** `cp .env.production.example .env.production`, fill every value (each has a comment saying how to generate it), `chmod 600 .env.production`, then `docker compose --env-file .env.production -f docker-compose.prod.yml up -d --build`. Update: `git pull` and the same command (it rebuilds, runs `migrate` again, and recreates what changed). Stop: `docker compose -f docker-compose.prod.yml down` (data stays in the `db_data` volume; add `-v` only to delete it).
- **Services.** `db` (postgres:16, no published port, on a network with no route to the internet; the app uses its own role `portfolio_app`, which owns only its database and cannot connect to the admin databases), `migrate` (one-shot `prisma migrate deploy`), `api` (non-root, read-only filesystem, no capabilities, `no-new-privileges`, memory-limited), `web` (nginx unprivileged on 8080, published on `127.0.0.1:${WEB_PORT}` only; serves the app, proxies `/api` to the API so there is no CORS, sets the security headers and a Content-Security-Policy that allows Google sign-in, Google Fonts and hCaptcha), `backup` (see below). Logs are JSON lines on stdout/stderr, rotated by Docker (3 x 10 MB).
- **Settings** (all read once at start by `apps/api/src/lib/config.ts`; production refuses to start and names the variable when one is missing or weak): `DATABASE_URL`, `JWT_SECRET` (>= 32 chars), `USER_HASH_SALT` (>= 32 chars), `PROFILE_ENCRYPTION_KEY`, `RP_ID` + `ORIGIN` (the passkey identity: the domain, and the exact https address; no localhost defaults in production), optional `GOOGLE_CLIENT_ID`, `ADMIN_EMAILS`, `PORT`, `BENCHMARK_REFRESH=off`, `HCAPTCHA_SITEKEY` + `HCAPTCHA_SECRET` (both or neither: the human check, optional), switches `ALLOW_REGISTRATION` (default true; false closes sign-up for everyone except the administrator's own first sign-in, answers 403 `REGISTRATION_CLOSED`), `ENABLE_DEMO` (default true in development, false in production unless set; the owner runs it on, so `.env.production.example` sets it to true. Off: `/api/auth/demo*` answer 404 and the login hides "Try the demo", which learns it from the public `GET /api/config`. On: every visit gets its own account, erased on sign-out and after an hour, see the demo above), `TRUST_PROXY` (number of reverse proxies in front of the API; the rate limit keys on the address it derives, so set it right: 1 for the web container alone).
- **Health.** `GET /api/health` (up, never touches the database) and `GET /api/ready` (a trivial query, 503 when the database cannot answer, nothing about why). The API shuts down cleanly on SIGTERM/SIGINT (finishes requests, stops the schedulers, disconnects the database).
- **Backups.** The `backup` service writes `./backups/portfolio-<time>.dump.age` daily, keeping 14, encrypted to the PUBLIC `age` key in `BACKUP_AGE_PUBLIC_KEY`; the private key never lives on the machine. Plain dumps exist only in memory. `infrastructure/backup/restore.md` has the setup, the restore (into an empty database, with the key given on standard input) and the optional off-machine copy hook. Practise a restore.
- **Rotating secrets.** `JWT_SECRET`: change it and restart; everyone signs in again. `APP_DB_PASSWORD` / `POSTGRES_ADMIN_PASSWORD`: change the role's password in Postgres (`ALTER ROLE ... PASSWORD ...`), then `.env.production`, then recreate the stack. **`USER_HASH_SALT` and `PROFILE_ENCRYPTION_KEY` cannot be rotated by editing the file**: the first orphans every account, the second makes stored data unreadable; there is no re-keying tool yet (the stored format is versioned for one). Keep copies of both.
- **Not done yet** (phases after this one): exposing the port to the internet with TLS, encrypting transactions/positions/cash/realized gains at field level, and an "add a passkey while signed in" flow.

## Clean Code & Engineering Standards

### 1. Pure, Deterministic Financial Calculation Engines (TDD)
- **Framework-Free Math:** Isolate all portfolio valuation, P&L, FIFO/LIFO lot matching, cost-basis calculations, Time-Weighted Return (TWR), and inflation-adjustment math into pure TypeScript functions[cite: 2, 9].
- **Test-Driven:** Write unit tests covering mathematical edge cases first (zero balance, stock splits, negative cash, multi-currency rounding discrepancies) before writing engine logic.
- **Zero Side Effects:** Never call `Date.now()`, `Math.random()`, or network fetches inside financial calculation helpers[cite: 5]. Pass timestamps, evaluation dates, and FX lookup tables explicitly as arguments[cite: 5].

### 2. Domain-Driven Design (DDD) & Ubiquitous Language
- Enforce unified domain naming across the Prisma schema, Express routes, backend services, and React state[cite: 4].
- Maintain consistent terminology stack-wide: use `Transaction`, `Holding`, `Lot`, and `RealizedGain` rather than alternating with words like "order" or "trade"[cite: 4].
- Encapsulate business logic inside domain entities instead of writing procedural controller code[cite: 4]. Apply "Tell, Don't Ask" (e.g., call `portfolio.calculateValueInCurrency(targetCurrency, fxMap)` rather than manually looping through transactions in a controller)[cite: 5].

### 3. Boundary Validation ("Parse, Don't Validate")
- Share Zod schemas between `apps/api` and `apps/web` to define common transaction shapes, currency formats, and payloads[cite: 3, 4].
- Enforce strict runtime parsing at API entry points[cite: 4]. Once parsed into trusted domain objects, eliminate downstream defensive checks like `typeof val === 'number'`[cite: 4].
- Never permit `any` or untyped loose strings to pass system boundaries[cite: 4].

### 4. Single Responsibility Principle (SRP)
- **Backend:** Express route handlers strictly parse HTTP requests; domain services compute metrics; Prisma models manage persistence[cite: 4]. Keep SQL queries and rebalancing math out of controllers[cite: 4].
- **Frontend:** Separate presentation from orchestration[cite: 4]. UI components receive typed props and render visuals; all data fetching, filtering, and mutations must reside in custom hooks (e.g., `useHoldings`)[cite: 4].

### 5. Dependency Inversion (DIP) & Hexagonal Adapters
- Never couple core valuation logic directly to external providers (Yahoo Finance, European Central Bank FX rates, or AlphaVantage) or database drivers.
- Define abstract interfaces (e.g., `PriceFetcher`, `InflationRateProvider`) and implement third-party HTTP clients as pluggable adapters.

### 6. Command-Query Separation (CQS) & Append-Only Ledger
- **Commands:** State-mutating operations (adding transactions, manual adjustments) update the database ledger and return simple acknowledgments[cite: 5]. Keep heavy recalculations off the write path[cite: 5].
- **Queries:** Net worth curves, tax summaries, and allocations are read-only computations[cite: 5].
- **Immutability:** Treat the transaction history as an append-only ledger[cite: 5]. Correct historical errors via offsetting adjustments rather than destructive row edits[cite: 5].

### 7. Centralized Design Tokens (DRY)
- Define all color hexes, typography scales, spacing, and border radii in the centralized Tailwind config (`tailwind.config.js`) or global CSS variables[cite: 3].
- Never use arbitrary ad-hoc utility classes (e.g., `text-[#1a1a1a]`)[cite: 3]. Use token names like `text-brand-primary` or `font-display`[cite: 3].

## Domain Features & Product Capabilities

- **Discipline Scorecard:** Automated audits for user-defined guardrails; flags non-Eurozone asset purchases, unexpected FX drag, and FOMO entries against technical indicators[cite: 2, 9].
- **Life-Event Overlays:** Chronological timeline tracking personal milestones (digital nomad travel, job shifts, relocations to/from Argentina) superimposed over portfolio PnL and volatility[cite: 1, 2, 8, 9].
- **True-Return Toggling:** One-click switches between Time-Weighted Return (TWR) and nominal returns, alongside inflation adjustments to reflect actual purchasing power[cite: 2, 9].
- **Auto-Tagging Exposure Matrix:** Automatic categorization of assets by geography, industry sector, and base currency to reveal concentration risk and cash drag[cite: 2, 9].
- **Routine & Timing Analytics:** Correlation engine analyzing execution timestamps versus outcome returns (e.g., morning versus late-afternoon trades).
- **Fixed Costs Tracker:** Dedicated module tracking monthly recurring expenses to provide integrated runway and guidance visuals[cite: 3, 10].
- **Silent Real-Time Updates:** Background updates powered by Server-Sent Events (SSE) to update prices and alerts without full-page reloads or layout shifts[cite: 3, 10].
- **Passkey WebAuthn Login:** Passwordless biometric authentication providing instant access[cite: 3, 10].
